# Tour Booking Roadmap

This document extends `CONTEXT.md`. Use the same domain language when planning and implementing this work:

- **Booker**: the person who provides contact information and receives booking communication.
- **Checkout Attempt**: a temporary record of selected tour details and payment state before a **Booking** exists.
- **Booking**: a paid reservation for a specific tour date, time, and party size.
- **Booking Communication**: a message sent to a **Booker** about a **Checkout Attempt** or **Booking**.

This roadmap is the working planning space for features that are not ready to become GitHub issues yet. Once a feature has enough detail, it should be split into small, independently grabbable issues for agents to implement through the established branch, commit, and PR workflow.

## 1. Post-Payment Booking Change Flow

Self-service edits are out of scope for the first paid checkout implementation. For v1, a **Booker** changes tour date, tour time, party size, or contact details by canceling the **Booking** before the cancellation cutoff and creating a new **Checkout Attempt**.

### Access Model

- After a **Booking** is completed, the **Booker** receives **Booking Communication** by email.
- The email includes a private manage link generated by the application.
- The manage link includes the **Booking** ID and a secret access token.
- The secret access token should be hashed at rest.
- For v1, the manage experience supports cancellation only, not self-service edits.

### V1 Change Behavior

- Tour date changes require canceling the **Booking** and creating a new **Checkout Attempt**.
- Tour time changes require canceling the **Booking** and creating a new **Checkout Attempt**.
- Party size changes require canceling the **Booking** and creating a new **Checkout Attempt**.
- Booker contact detail changes are not self-service in v1.

### Future Edit Behavior

- A later edit flow may allow changing Booker contact details without payment changes.
- A later edit flow may allow changing date, time, or party size if payment adjustments, refunds, additional charges, capacity changes, and Booking Communication rules are defined.
- A pending change request flow may be added later if operational review becomes necessary.

### Product Questions

- Should the edit link expire?
- Should future edit access use the same manage link token as cancellation?
- Should contact detail edits notify both old and new Booker email addresses?
- Should date, time, or party size edits be modeled as a cancellation plus new Checkout Attempt, even after v1?
- Should payment adjustments be automatic or require operational review?
- Should the system record when and how a **Booking** was edited?

### Acceptance Criteria Draft

- A **Booker** cannot self-service edit a paid **Booking** in v1.
- A **Booker** can cancel a paid **Booking** before the cancellation cutoff and create a new **Checkout Attempt**.
- Manage route copy does not promise self-service date, time, party size, or contact detail edits.
- Future edit behavior is not implemented until payment and capacity adjustment rules are defined.

### Issue Candidates

- Revise manage route copy to remove self-service edit promises.
- Decide future contact-detail edit behavior.
- Decide future date, time, and party size change behavior.
- Decide whether future changes should reuse cancellation plus new Checkout Attempt.

## 2. Booking Cancel Flow

A **Booker** should be able to cancel an existing **Booking** if they can no longer attend the tour.

### Access Model

- After a **Booking** is completed, the **Booker** receives **Booking Communication** by email.
- The email includes a private manage or cancel link generated by the application.
- The link points to a route for the specific **Booking** using the booking ID and a secret access token.
- The secret access token should be hashed at rest.
- Clicking the cancel link takes the **Booker** directly to the cancel experience for that **Booking**.

### Cancellation Behavior

- The **Booker** should review the **Booking** details before confirming cancellation.
- Cancellation should not happen from the email click alone.
- The **Booker** should explicitly confirm the cancellation.
- Self-service cancellation is available only before the 24-hour cancellation cutoff.
- Self-service cancellation inside the 24-hour cutoff should be blocked and direct the **Booker** to contact support.
- Refund creation must succeed before the **Booking** is marked canceled.
- After refund creation succeeds, **Booking Status** becomes canceled and **Payment Status** becomes refund pending.
- Canceled **Bookings** release capacity immediately, even while the refund is pending.
- Stripe refund webhook handling updates **Payment Status** to refunded or refund failed.
- The **Booking** should be marked canceled rather than deleted.
- Refunds are full refunds for v1.
- Partial guest cancellation, cancellation fees, and discretionary in-app refunds are out of scope for v1.

### Product Questions

- Should the manage link token remain valid indefinitely or expire after the tour?
- Should the **Booker** provide a cancellation reason?
- Should admins or tour guides see canceled **Bookings** by default?
- Should refund failure trigger internal operational notification in addition to Booking Communication?

### Acceptance Criteria Draft

- A **Booker** can open a private cancel or manage link from **Booking Communication**.
- A **Booker** can review the current **Booking** details before canceling.
- A **Booker** can confirm cancellation intentionally before the 24-hour cancellation cutoff.
- Cancellation inside the 24-hour cutoff is blocked from self-service.
- If Stripe refund creation fails, the **Booking** remains active and the **Booker** receives clear retry or support guidance.
- If Stripe refund creation succeeds, the **Booking** is marked canceled and no longer treated as active.
- The **Booker** receives **Booking Communication** when cancellation is confirmed and refund has been requested.
- If Stripe later reports refund failure, **Payment Status** is updated and the **Booker** receives failure communication.

### Issue Candidates

- Generate hashed access tokens for completed **Bookings**.
- Add private manage or cancel link content to **Booking Communication**.
- Add cancel route access validation using Booking ID and token.
- Add cancellation confirmation UI with 24-hour cutoff enforcement.
- Create Stripe refunds for eligible cancellations.
- Persist **Booking Status** and **Payment Status** changes.
- Send cancellation **Booking Communication** after refund request succeeds.
- Handle Stripe refund webhook updates.

## 3. Admin Dashboard Route

Admins need a private route for monitoring and managing **Bookings** across tours.

The term **Admin** is intentionally introduced here as a planning term. It should be added to `CONTEXT.md` once the dashboard feature is ready to be implemented and the domain language is stable.

### Primary Goals

- Give admins visibility into upcoming **Bookings**.
- Help admins support **Bookers** who need changes or cancellations.
- Give admins enough operational context to understand tour demand and capacity.

### Capabilities

- View upcoming **Bookings**.
- View past **Bookings**.
- Search or filter **Bookings**.
- Inspect **Booker** contact details.
- Inspect tour date, tour time, and party size.
- Edit a **Booking** on behalf of a **Booker**.
- Cancel a **Booking** on behalf of a **Booker**.
- Review **Booking Communication** status, if available.

### Product Questions

- How are admins authenticated?
- Who can become an admin?
- Should admin access be role-based?
- What filters are required for the first version?
- Should admins see canceled **Bookings** by default?
- Should admin edits trigger **Booking Communication**?
- Should admin actions be recorded for audit purposes?

### Acceptance Criteria Draft

- An admin can access a private dashboard route.
- Non-admin visitors cannot access the dashboard route.
- An admin can see a list of **Bookings**.
- An admin can inspect the details for a specific **Booking**.
- An admin can understand whether a **Booking** is active or canceled.

### Issue Candidates

- Define admin authentication and authorization approach.
- Add private admin dashboard route.
- Add **Booking** list view for admins.
- Add **Booking** detail view for admins.
- Add admin edit action for **Bookings**.
- Add admin cancel action for **Bookings**.
- Add dashboard filters and search.

## 4. Tour Guide View

Tour guides need a focused view that helps them successfully lead a specific tour.

The term **Tour Guide** is intentionally introduced here as a planning term. It should be added to `CONTEXT.md` once the tour guide feature is ready to be implemented and the domain language is stable.

### Primary Goals

- Give tour guides the exact information needed for a tour.
- Keep the view focused on the tour date and tour time they are leading.
- Avoid exposing admin-only management tools unless needed.

### Capabilities

- View the tour date and tour time.
- View all active **Bookings** for that tour.
- View **Bookers** for that tour.
- View party size per **Booking**.
- View total guest count for the tour.
- View relevant tour specifics or notes, if available.
- Distinguish active **Bookings** from canceled **Bookings**, if canceled records are shown.

### Product Questions

- How are tour guides authenticated?
- Can a tour guide see all tours or only assigned tours?
- What information about a **Booker** should a tour guide see?
- Should tour guides see contact details?
- Should tour guides be able to mark attendance?
- Should tour guides be able to report issues after a tour?
- Should canceled **Bookings** be hidden by default?

### Acceptance Criteria Draft

- A tour guide can access a route for a specific tour.
- A tour guide can see the date and time for that tour.
- A tour guide can see all active **Bookings** for that tour.
- A tour guide can see each **Booker** and party size.
- A tour guide can see the total expected guest count.

### Issue Candidates

- Define tour guide authentication and authorization approach.
- Add tour guide route for a specific tour.
- Add tour guide tour summary view.
- Add tour guide **Booking** roster.
- Add total guest count calculation.
- Add assigned-tour access rules, if required.

## 5. Checkout Flow

A **Booker** should pay for selected tour details through Stripe Checkout before a **Booking** is created.

### Payment Provider

- Use Stripe Checkout Sessions for the first payment implementation.
- Use `mode: "payment"` because tour bookings are one-time payments.
- Use Stripe-hosted Checkout for payment collection.
- Do not manage Stripe Customers in v1; use guest Checkout with the **Booker** email passed as `customer_email`.
- Allow Stripe receipts for payment proof, while **Booking Communication** remains responsible for tour-specific details.
- Store Stripe Checkout Session ID on the **Checkout Attempt**.
- Store Stripe PaymentIntent ID on the paid **Booking** for refunds and support.

### Checkout Attempt Model

- Persist a **Checkout Attempt** before redirecting the **Booker** to Stripe Checkout.
- A **Checkout Attempt** stores selected tour date, tour time, party size, Booker contact details, pricing snapshot, Stripe Checkout Session ID, Payment Status, expiration time, and hashed access token.
- A **Checkout Attempt** expires after 30 minutes.
- A **Checkout Attempt** does not reserve tour capacity.
- If a **Booker** changes party size, date, time, or contact details before payment, create a new **Checkout Attempt** and Stripe Checkout Session.
- Multiple active **Checkout Attempts** are allowed. Idempotency is enforced per internal Checkout Attempt and Stripe Checkout Session, not by email or matching tour details.

### Dynamic Pricing Model

- Prices are per guest for v1.
- Calculate the charge amount server-side from selected tour details and party size.
- Store a pricing snapshot on the **Checkout Attempt** and honor it until the attempt expires.
- Do not trust client-provided prices or totals.
- Use Checkout Session `line_items` with inline `price_data` because the final amount depends on selected tour details and party size.
- Use `quantity` for guest count and `price_data.unit_amount` for the per-guest price in the smallest currency unit.
- Set `price_data.currency` explicitly.
- Stripe Tax is disabled for v1 and should be revisited before production if tax collection is required for guided tours.

### Access Tokens

- Generate a random secret access token when creating the **Checkout Attempt**.
- Store the hashed token, not the raw token.
- Include the raw token only in private success, cancel, and manage URLs.
- Carry the same access token from **Checkout Attempt** to **Booking** after payment succeeds.
- For v1, manage link tokens do not expire, but they do not override cancellation cutoff rules.

### Completion Behavior

- A **Booking** must be created only by verified Stripe webhook handling.
- A **Booking** should not become complete only because the **Booker** returns to the success URL.
- The success route shows **Checkout Attempt** payment processing state until the webhook creates the **Booking**.
- At webhook time, verify the **Checkout Attempt**, Stripe amount, Payment Status, and current capacity.
- Check current tour capacity at webhook time rather than relying on capacity from the pricing snapshot.
- If payment succeeds but capacity is no longer available, automatically refund the payment, do not create a **Booking**, mark the **Checkout Attempt** failed, and send **Booking Communication** explaining the refund.
- If a Checkout Session expires, mark the **Checkout Attempt** expired, do not create a **Booking**, and do not send Booking Communication.

### Required Stripe Webhooks

- `checkout.session.completed` creates the **Booking** after validation succeeds.
- `checkout.session.expired` marks the **Checkout Attempt** expired.
- `charge.refunded` or `refund.updated` updates refund **Payment Status** after cancellation.

### Product Questions

- Should failed-capacity refunds trigger operational alerts in addition to Booking Communication?
- Should manage link tokens eventually expire after the tour date?
- Should Stripe Tax be enabled after tax obligations are reviewed?
- Should future group pricing switch Checkout line items from per-guest quantity to a single total line item?

### Acceptance Criteria Draft

- A **Booker** can start Checkout from reviewed tour details.
- The server validates selected tour details and calculates the Stripe amount.
- A **Checkout Attempt** is persisted before Stripe redirect.
- Stripe Checkout displays the correct tour purchase and guest quantity.
- A successful Stripe webhook creates the **Booking** only after amount and capacity validation pass.
- A success URL cannot create a **Booking** without webhook confirmation.
- Expired Checkout Sessions do not create **Bookings**.
- Paid Checkout Sessions that fail capacity validation are automatically refunded and do not create **Bookings**.
- Paid **Bookings** trigger required **Booking Communication**.

### Issue Candidates

- Add **Checkout Attempt** domain model and hashed access tokens.
- Add Stripe configuration and create Checkout Session endpoint or action.
- Add Checkout success and cancel status routes.
- Add webhook endpoint for Checkout completion and expiration.
- Create **Bookings** from webhook after amount and capacity validation.
- Add paid **Booking Communication**.
- Add cancellation and refund flow with cutoff enforcement.
- Add refund webhook handling and refund status updates.
- Revise manage route copy to remove self-service edit promises.
- Add tests around capacity race, duplicate webhook delivery, expired attempts, cancellation cutoff, and refund failure.

## 6. Cross-Feature Considerations

### Access Security

Checkout, manage, and cancel links should not rely on IDs alone if the links can expose or mutate private **Checkout Attempt** or **Booking** details. Use random secret access tokens and store hashed tokens at rest.

### Booking Status

The application needs explicit **Booking Status** and **Payment Status** values before checkout, cancellation, refunds, admin management, and tour guide views are implemented.

### Booking Communication

Checkout, cancellation, and refund flows affect **Booking Communication**. The project should decide which events trigger messages:

- **Checkout Attempt** paid and **Booking** created.
- **Checkout Attempt** paid but refunded because capacity is no longer available.
- **Booking** canceled by the **Booker**.
- **Booking** refund failed after cancellation.
- **Booking** edited by the **Booker**, if future edit behavior is added.
- **Booking** canceled by an admin.

### Route Planning

Potential routes to discuss before implementation:

- `/booking/:bookingId/edit`
- `/booking/:bookingId/cancel`
- `/checkout/:checkoutAttemptId/success`
- `/checkout/:checkoutAttemptId/cancel`
- `/manage/:bookingId`
- `/admin`
- `/admin/bookings`
- `/admin/bookings/:bookingId`
- `/guide/tours/:tourId`

These are placeholders for planning only and should be validated against the existing route structure before implementation.

## 7. Issue Readiness Checklist

A feature is ready to become GitHub issues when it has:

- Clear actor definitions.
- Clear route entry points.
- Required data fields.
- Required state changes.
- Acceptance criteria.
- Security and access rules.
- Verification expectations.
- Known risks or assumptions.
- A small first vertical slice.

Each issue should be independently grabbable by an agent and should map to a contained PR.
