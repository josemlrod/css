# Tour Booking Roadmap

This document extends `CONTEXT.md`. Use the same domain language when planning and implementing this work:

- **Booker**: the person who provides contact information and receives booking communication.
- **Booking**: a reservation request for a specific tour date, time, and party size.
- **Booking Communication**: a message sent to a **Booker** about a **Booking**.

This roadmap is the working planning space for features that are not ready to become GitHub issues yet. Once a feature has enough detail, it should be split into small, independently grabbable issues for agents to implement through the established branch, commit, and PR workflow.

## 1. Booking Edit Flow

A **Booker** should be able to return to an existing **Booking** and update details after the original booking flow is complete.

### Access Model

- After a **Booking** is completed, the **Booker** receives **Booking Communication** by email.
- The email includes an edit link generated by the application.
- The edit link points to a route for the specific **Booking** using the booking ID.
- Clicking the edit link takes the **Booker** directly to the edit experience for that **Booking**.

### Editable Fields

- Tour date.
- Tour time.
- Party size.
- Booker contact details.

### Update Behavior

- For the first version, edits immediately update the existing **Booking**.
- A pending change request flow may be added later if operational review becomes necessary.

### Product Questions

- Should the edit link expire?
- Should edit access require a token in addition to the booking ID?
- Should any fields become locked close to the tour date or tour time?
- Should an updated **Booking** trigger new **Booking Communication**?
- Should the system record when and how a **Booking** was edited?

### Acceptance Criteria Draft

- A **Booker** can open an edit link from **Booking Communication**.
- A **Booker** can view the current **Booking** details before changing them.
- A **Booker** can update tour date, tour time, party size, and contact details.
- The existing **Booking** reflects the saved changes immediately.
- The **Booker** receives clear success or failure feedback.

### Issue Candidates

- Generate edit links for completed **Bookings**.
- Add edit link content to **Booking Communication**.
- Add edit route for a specific **Booking**.
- Load existing **Booking** details into an edit form.
- Persist edits to an existing **Booking**.
- Send updated **Booking Communication** after edits, if required.

## 2. Booking Cancel Flow

A **Booker** should be able to cancel an existing **Booking** if they can no longer attend the tour.

### Access Model

- After a **Booking** is completed, the **Booker** receives **Booking Communication** by email.
- The email includes a cancel link generated by the application.
- The cancel link points to a route for the specific **Booking** using the booking ID.
- Clicking the cancel link takes the **Booker** directly to the cancel experience for that **Booking**.

### Cancellation Behavior

- The **Booker** should review the **Booking** details before confirming cancellation.
- Cancellation should not happen from the email click alone.
- The **Booker** should explicitly confirm the cancellation.
- The **Booking** should be marked canceled rather than deleted.

### Product Questions

- Should the cancel link expire?
- Should cancel access require a token in addition to the booking ID?
- Should cancellation be blocked close to the tour date or tour time?
- Should the **Booker** provide a cancellation reason?
- Should cancellation trigger **Booking Communication**?
- Should admins or tour guides see canceled **Bookings** by default?

### Acceptance Criteria Draft

- A **Booker** can open a cancel link from **Booking Communication**.
- A **Booker** can review the current **Booking** details before canceling.
- A **Booker** can confirm cancellation intentionally.
- The **Booking** is marked canceled and no longer treated as active.
- The **Booker** receives clear success or failure feedback.

### Issue Candidates

- Generate cancel links for completed **Bookings**.
- Add cancel link content to **Booking Communication**.
- Add cancel route for a specific **Booking**.
- Add cancellation confirmation UI.
- Persist canceled status on a **Booking**.
- Send cancellation **Booking Communication**, if required.

## 3. Admin Dashboard Route

Admins need a private route for monitoring and managing **Bookings** across tours.

The term **Admin** is intentionally introduced here as a planning term. It should be added to `CONTEXT.md` once the dashboard feature is ready to be implemented and the domain language is stable.

### Primary Goals

- Give admins visibility into upcoming **Bookings**.
- Help admins support **Bookers** who need changes or cancellations.
- Give admins enough operational context to understand tour demand and capacity.

### Capabilities

- View upcoming **Bookings**.
- View past **Bookings**.
- Search or filter **Bookings**.
- Inspect **Booker** contact details.
- Inspect tour date, tour time, and party size.
- Edit a **Booking** on behalf of a **Booker**.
- Cancel a **Booking** on behalf of a **Booker**.
- Review **Booking Communication** status, if available.

### Product Questions

- How are admins authenticated?
- Who can become an admin?
- Should admin access be role-based?
- What filters are required for the first version?
- Should admins see canceled **Bookings** by default?
- Should admin edits trigger **Booking Communication**?
- Should admin actions be recorded for audit purposes?

### Acceptance Criteria Draft

- An admin can access a private dashboard route.
- Non-admin visitors cannot access the dashboard route.
- An admin can see a list of **Bookings**.
- An admin can inspect the details for a specific **Booking**.
- An admin can understand whether a **Booking** is active or canceled.

### Issue Candidates

- Define admin authentication and authorization approach.
- Add private admin dashboard route.
- Add **Booking** list view for admins.
- Add **Booking** detail view for admins.
- Add admin edit action for **Bookings**.
- Add admin cancel action for **Bookings**.
- Add dashboard filters and search.

## 4. Tour Guide View

Tour guides need a focused view that helps them successfully lead a specific tour.

The term **Tour Guide** is intentionally introduced here as a planning term. It should be added to `CONTEXT.md` once the tour guide feature is ready to be implemented and the domain language is stable.

### Primary Goals

- Give tour guides the exact information needed for a tour.
- Keep the view focused on the tour date and tour time they are leading.
- Avoid exposing admin-only management tools unless needed.

### Capabilities

- View the tour date and tour time.
- View all active **Bookings** for that tour.
- View **Bookers** for that tour.
- View party size per **Booking**.
- View total guest count for the tour.
- View relevant tour specifics or notes, if available.
- Distinguish active **Bookings** from canceled **Bookings**, if canceled records are shown.

### Product Questions

- How are tour guides authenticated?
- Can a tour guide see all tours or only assigned tours?
- What information about a **Booker** should a tour guide see?
- Should tour guides see contact details?
- Should tour guides be able to mark attendance?
- Should tour guides be able to report issues after a tour?
- Should canceled **Bookings** be hidden by default?

### Acceptance Criteria Draft

- A tour guide can access a route for a specific tour.
- A tour guide can see the date and time for that tour.
- A tour guide can see all active **Bookings** for that tour.
- A tour guide can see each **Booker** and party size.
- A tour guide can see the total expected guest count.

### Issue Candidates

- Define tour guide authentication and authorization approach.
- Add tour guide route for a specific tour.
- Add tour guide tour summary view.
- Add tour guide **Booking** roster.
- Add total guest count calculation.
- Add assigned-tour access rules, if required.

## 5. Cross-Feature Considerations

### Access Security

Edit and cancel links should not rely on booking ID alone if the links can expose or mutate private **Booking** details. A signed token, secret link token, expiration policy, or similar mechanism may be needed before implementation.

### Booking Status

The application likely needs an explicit **Booking** status, such as active or canceled, before cancellation, admin management, and tour guide views are implemented.

### Booking Communication

Edit and cancel flows both affect **Booking Communication**. The project should decide which events trigger messages:

- Original **Booking** completed.
- **Booking** edited by the **Booker**.
- **Booking** canceled by the **Booker**.
- **Booking** edited by an admin.
- **Booking** canceled by an admin.

### Route Planning

Potential routes to discuss before implementation:

- `/booking/:bookingId/edit`
- `/booking/:bookingId/cancel`
- `/admin`
- `/admin/bookings`
- `/admin/bookings/:bookingId`
- `/guide/tours/:tourId`

These are placeholders for planning only and should be validated against the existing route structure before implementation.

## 6. Issue Readiness Checklist

A feature is ready to become GitHub issues when it has:

- Clear actor definitions.
- Clear route entry points.
- Required data fields.
- Required state changes.
- Acceptance criteria.
- Security and access rules.
- Verification expectations.
- Known risks or assumptions.
- A small first vertical slice.

Each issue should be independently grabbable by an agent and should map to a contained PR.
