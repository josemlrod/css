Core Flow

Tour Booking Flow

Booker selects tour details and opens PayPal or guest card checkout in the booking stepper. The server captures an approved PayPal Order and creates the Booking only after payment and capacity checks pass.

Invariant

Return routes never create Bookings. Only a server-verified PayPal capture can create one, either from the synchronous capture response or a verified PAYMENT.CAPTURE.COMPLETED webhook.

Entities

Tour

Catalog item with price, capacity, start times, meeting point.

Checkout Attempt

Temporary payment record. Stores selected details, pricing snapshot, paypalOrderId, status, expiry, token hash.

Booking

Paid reservation. Created only after verified payment and capacity re-check. Stores paypalCaptureId, token hash, cancel/refund state.

Booking Communication

Email sent by app for tour details, refund notices, cancellation results, and refund failures. PayPal receipts stay separate.

PayPal Migration State

Payment persistence uses paypalOrderId, paypalCaptureId, and paypalRefundId. New Checkout Attempts now create PayPal Orders from embedded SDK v6 buttons. The capture action creates Bookings or starts PayPal refunds after a capacity race. The verified PayPal webhook provides an idempotent backup for completed captures and handles failed captures, approval reversals, and refund results.

Checkout Start

1

Booker chooses PayPal or card

paypal-buttons.tsx validates the confirm-step data before posting date, time, guests, name, and email.

2

Checkout Attempt created

saveCheckoutAttempt stores pending status, 30-minute expiry, pricing snapshot, hashed access token.

3

PayPal Order created

The action computes the total from Tour price and guest count, calls createPayPalOrder, and stores paypalOrderId.

4

SDK opens checkout

The action returns the Order ID to SDK v6. PayPal or the guest card form opens over the confirm step without a Stripe redirect.

5

Checkout canceled

Closing the PayPal overlay sends the Booker to /checkout/cancel/:checkoutAttemptId?token=.... This ends the payment flow without creating a Booking.

Payment Received

1

Order captured

The SDK approval callback posts the private Checkout Attempt token and Order ID to /paypal/capture/:checkoutAttemptId. The server verifies both before calling PayPal.

2

Attempt reconciled

A completed capture passes its amount, currency, Order ID, and Capture ID to finalizePaidCapture. completeCheckoutAttempt checks idempotency and current capacity.

3

Booking created

If capacity exists, the app inserts the Booking with paymentStatus: paid and marks the attempt paid. A pending PayPal capture leaves the attempt pending.

4

Email sent

App sends Booking details and private /manage/:bookingId?token=... link.

Pending or Expired

The token-protected checkout cancel route only displays Checkout Attempt state; it does not cancel a paid Booking. If payment never completes, Convex schedules the pending Checkout Attempt to become expired at its 30-minute deadline. A verified CHECKOUT.PAYMENT-APPROVAL.REVERSED event can also expire a still-pending attempt by PayPal Order ID.

Manual check: create a Checkout Attempt and leave it unpaid, then confirm paymentStatus = expired after 30 minutes. For a faster check, run expireIfPending from the Convex dashboard.

Capacity Race

Checkout Attempts do not reserve capacity. If payment succeeds after capacity fills, the shared finalizer creates no Booking, marks the attempt refund_pending, creates a full PayPal refund, stores the refund ID, and emails the Booker.

Self-Service Cancellation

Manage route requires Booking ID plus raw token. Before the 24-hour cutoff, refund creation must succeed first. Then Booking becomes canceled, capacity releases, and Payment Status becomes refund_pending.

Refund Lifecycle

The PayPal refund response records refunded, refund_pending, or refund_failed with its paypalRefundId. Verified PAYMENT.CAPTURE.REFUNDED and PAYMENT.REFUND.FAILED events finalize Payment Status by that refund ID. Refund failures send Booking Communication only when the mutation changes a record.

Scenario Entity State Booking? Communication
Checkout started Checkout Attempt.paymentStatus = pending No None
Payment succeeds, capacity available Checkout Attempt = paid, Booking = paid Yes Booking details email with manage link
Payment succeeds, capacity full Checkout Attempt = refund_pending, then refunded or refund_failed No Capacity refund email; failure email if PayPal fails refund
Scheduled expiry or PayPal approval reversal Checkout Attempt = expired No None
Booker cancels before cutoff Booking.cancelled != null, Booking.paymentStatus = refund_pending Canceled Cancellation/refund requested email
PAYMENT.CAPTURE.REFUNDED paymentStatus = refunded Unchanged None
PAYMENT.REFUND.FAILED paymentStatus = refund_failed Unchanged Refund failure email

Code Map

convex/schema.ts

Tour, Checkout Attempt, Booking fields and payment status vocabulary.

app/routes/tour-booking.tsx

Validates Booker input, creates a Checkout Attempt and PayPal Order, then returns the Order ID to SDK v6.

app/components/stepper/paypal-buttons.tsx

Loads SDK v6, starts payment sessions, captures approved Orders, and handles cancellation.

app/routes/paypal-capture.ts

Verifies the private token and Order ID, captures through PayPal, and routes the result by payment status.

app/lib/checkout-completion.ts

Creates paid Bookings and Booking Communication, or refunds captures after a capacity race.

app/lib/stripe.ts

Creates Checkout Sessions, verifies webhooks, creates refunds.

convex/checkoutAttempts.ts

Completes attempts, schedules pending-attempt expiry, and handles refund status by the persisted PayPal refund ID.

app/routes/paypal-webhook.ts

Handles verified PayPal events for payment completion, failure, approval reversal, and refund lifecycle.

app/routes/manage-tour.tsx

Validates private token, enforces 24-hour cutoff, starts cancellation refunds.

convex/bookings.ts

Token-scoped Booking lookup and cancellation mutation.

app/lib/email.ts

Booking Communication content and send functions.
