Switching Checkout from Stripe to PayPal

What the current Stripe integration does, which PayPal product actually fits it, how the webhook model changes, and whether the swap removes or adds code. Domain terms follow CONTEXT.md: Booker, Checkout Attempt, Booking, Booking Communication.

Short answer

PayPal's no-code Buy Button does accept cards, but it cannot power this app. The workable path is PayPal's low-code JS SDK v6 buttons plus the Orders v2 API. That path is a net increase of roughly 250 to 400 lines of app code and a modest increase in complexity, mostly because PayPal makes us do the payment capture step and the webhook signature check that Stripe Checkout did for us.

Why the no-code button fails here

  • Fixed price per button. Our amount is guests × tour.price, computed server-side and snapshotted on the Checkout Attempt. A dashboard button can't take a per-attempt total.
  • No reference back to our record. Dashboard buttons expose no custom_id or invoice_id, so a webhook can't be matched to a Checkout Attempt. That breaks amount verification, the capacity re-check, and Booking creation.
  • No per-attempt return URLs. Our success and cancel routes carry the attempt ID and raw access token.
  • Refunds still need the API. Self-service cancellation needs a stored capture ID, which only the API path gives us.

You were right that the button accepts cards (PayPal lists PayPal, Pay Later, Venmo, Apple Pay, and major cards). The blocker is reconciliation, not payment methods.

Three ways to integrate PayPal, and which one to pick

Not viable

A. No-code Buy Button / Pay Link

Dashboard-generated HTML. Cards, Apple Pay, PayPal, Venmo all supported on PayPal's hosted page.

  • Fixed or customer-set price only
  • No custom_id to link a Checkout Attempt
  • No per-attempt return URLs
  • Would force dropping capacity re-check and self-service refunds
Fallback

B. Server redirect (Orders v2 payer-action link)

Closest to today's Stripe Checkout shape: create order, redirect Booker to PayPal, they come back, we capture.

  • No client JS, smallest diff
  • Card guest checkout is not guaranteed. PayPal shows "Pay with Debit or Credit Card" based on risk factors it controls, even with "PayPal account optional" on
  • No Apple Pay or Google Pay on the hosted page
  • Still needs the capture step and webhook handler
Recommended

C. JS SDK v6 buttons + Orders v2 (low-code)

Buttons render on our confirm step. createOrder and onApprove call our server. Booker never leaves the site.

  • paypal-payments: PayPal and Pay Later
  • paypal-guest-payments: a standalone debit/credit card button that does not require Advanced Checkout onboarding. This is the card guarantee
  • applepay-payments, googlepay-payments: available after Advanced Checkout onboarding (bonus, phase 2)
  • Server keeps full control of amount, Checkout Attempt, capture, and refunds

Webhook dynamics: what actually changes

The biggest conceptual shift. Stripe Checkout captured for us, so the webhook was the first moment we knew a payment succeeded. PayPal makes us capture, and the capture API response is a synchronous, server-to-server confirmation. The webhook becomes a reconciliation path rather than the only path.

Complexity: what goes up

  • Two completion entry points. Capture response and webhook both call the finalizer. The existing booking_exists and already_updated branches already make this safe, but reviewers must hold both paths in their head.
  • A pending payment state that can last hours. Stripe Checkout never handed us an unsettled card payment. PayPal can. The success page copy already fits; the missing piece is making sure a PENDING capture does not send Booking Communication.
  • Client-side payment UI. A script tag, eligibility checks, and callbacks live in the stepper. Today the stepper knows nothing about payments.
  • Webhook verification by hand. Either an OAuth round trip per webhook or an RSA verify with certificate fetching and host allow-listing (paypal-cert-url must be a *.paypal.com host).
  • Expiry without a webhook. Needs a scheduler or an accepted pile of stale pending rows.

Complexity: what stays the same or improves

  • Checkout Attempt model is untouched. Pending → paid/expired/failed/refund_* vocabulary maps one-to-one. Token hashing, 30-minute TTL, pricing snapshot, capacity re-check: all unchanged.
  • Refund flow is the same shape. Refund first, then cancel, then email. Only the API call and ID field change.
  • Booking Communication is unchanged except two copy strings.
  • Duplicate payment guard gets stronger. invoice_id uniqueness is enforced by PayPal's account, not only by our mutation.
  • Faster confirmation for the Booker. The Booking exists before the success page renders in the common case, instead of "Payment processing" until a webhook lands.

What you need to gather

  • PayPal Business account with "PayPal account optional" set to On (Account Settings → Website payments → Website preferences). This enables guest card checkout inside the PayPal overlay.
  • REST app in the Developer Dashboard, sandbox and live: PAYPAL_CLIENT_ID, PAYPAL_CLIENT_SECRET. The client ID is public and also needed in the browser as VITE_PAYPAL_CLIENT_ID.
  • Webhook registered on that app pointing at https://<APP_ORIGIN>/paypal/webhook, subscribed to the five events above. Save the generated PAYPAL_WEBHOOK_ID.
  • PAYPAL_ENV=sandbox|live to pick api-m.sandbox.paypal.com vs api-m.paypal.com.
  • For Apple Pay: enable "Advanced Credit and Debit Card Payments" and tick Apple Pay under the app's Features; register the production domain; host the domain association file at /.well-known/apple-developer-merchantid-domain-association. Sandbox testing needs a real Apple device in Safari.
  • For Google Pay: same feature enablement, no domain registration.
  • Sandbox buyer accounts (personal, plus a card-only guest) from the Developer Dashboard for end-to-end testing.

Risks and open questions

  • Decide first Live Stripe Bookings with future tour dates. Their refunds can only go through Stripe. If any exist in production, the manage route must branch on provider (keep stripe* fields optional and createRefundForPaymentIntent alive) until they age out. If production has none, this is a clean swap. Please confirm which case applies.
  • Schema Renaming fields breaks Convex schema validation on existing rows. Options: keep old fields as optional, or run a one-off migration.
  • Pending captures PayPal balance payments funded by bank transfer can stay PENDING for days. Copy on the success page and in the pending state should not promise the tour is held, because a Checkout Attempt does not reserve capacity.
  • Runtime Production Docker image is node:20-alpine. Local webhook verification with zlib.crc32 needs Node 22.2+. Either bump the image or use PayPal's verify endpoint.
  • Webhook reliability PayPal delivery is slower and flakier than Stripe's. The capture-on-approve design means the webhook is rarely on the critical path, which is the point.
  • Apple Pay Only works on registered domains over HTTPS in Safari. Treat it as a separate issue after cards and PayPal are live.
  • Statement descriptor Card statements show PAYPAL *CSSTOURS style text (22-char soft_descriptor). Worth setting so Bookers recognize the charge.
